## 这是什么

原理和李跳跳一类工具相同，三步：

```
读取当前窗口的控件节点树  →  在本地按规则匹配「跳过」类按钮  →  模拟点击
```

- **一次整树遍历 + 本地匹配**：每个扫描轮次只取一次 `rootInActiveWindow`，在同一棵树上同时匹配控件 id 与文字，不再调用会在 WebView 上阻塞数秒的系统文本检索接口。
- **规则驱动**：内置规则 + 自己的规则库 + 学到的规则 + 自定义规则分层合并；只认「跳过 / 跳过广告 / 关闭广告 / 关闭开屏」这类明确的跳过词，「关闭」不算。
- **保守的防误点**：冷启动监测窗口、时间节流的扫描、内容页闸门（有滚动列表 / 可点击元素过多就不自识别）、连续两轮同位置才动作；浏览器、系统设置、安装器等整体不扫描。
- **不学习坐标规则**：早期版本会因学错坐标而在每次打开 App 时误点固定位置，v1.1.0 起彻底移除，并自动清理历史数据。
- **ROM 兼容处理**：前台服务 + 1×1 透明微窗，解决部分 HyperOS / MIUI 上「无障碍开着却拿不到正确窗口、进程被后台冻结」的问题。

## v1.9.0 做了什么：把规则库收回来自己管

以前默认拉的是社区那份 `BasicRules.json`：规则怎么写、什么时候改、改坏了怎么回滚，
全在别人手里；而且那份是李跳跳哈希数组，连包名都读不出来，出问题无从查起。

现在规则源是本仓库的 `rules_server/rules.json`，内容由 `tools/build_rules.py` 合成：

```
base.json（社区快照，原样）  +  overrides.json（自己维护的修正）
                              ↓
                    rules.json（带 version / updatedAt）
```

- **三层分得清**：上游改版只影响 `base.json`，自己改的永远在 `overrides.json` 里，
  产物每次重算，任何一条规则从哪来都查得到。
- **构建时就挡掉写坏的规则**：`when`/`action` 为空、两边完全相同（会点到自己）、
  弹窗超过 40 条，直接拒绝写文件。
- **版本号有意义**：内容变了才 `version + 1`；App 里显示「v4 · 345 条规则 · 11-28 更新」，
  点「获取最新规则」会告诉你 `v3 → v4`，而不是一句含糊的「已是最新」。
- **手动入口**：「规则管理」顶部新增「获取最新规则」，走 `force` 同步（不带 ETag、
  带 `Cache-Control: no-cache`），成功后立即 `reloadRules()`，不用等下次重启服务。
- **四路镜像**：jsDelivr（两个节点）/ GitHub Pages / raw.githubusercontent，
  30 秒总预算内依次尝试，结果里写明实际来源域名。

维护方式见 [`rules_server/README.md`](rules_server/README.md)。
收到用户回传的规则（问卷 [28867380](https://wj.qq.com/s2/28867380/8kz9/)）不用手抄：
`python tools/from_survey.py 导出.xlsx` 会把整张表扫一遍并写进 `overrides.json`。

## v1.8.0 做了什么：现场学一条弹窗规则

规则永远追不上 App 改版。「618 主会场」改成「双 11 主会场」，写死文案的规则当场失效，
而这个开关叫「关闭应用内弹窗」，用户自然以为它应该什么都能关。与其追着改文案，
不如让他自己在弹窗上戳一下。

**怎么用**：首页点「教它关弹窗」→ 屏幕上多出一个琥珀色的「学」球 → 切到有弹窗的 App，
等弹窗出来 → **点一下「学」球** → 屏幕盖上一层提示 → **点一下那个关不掉的按钮**。
学完立刻生效；长按「学」球可以把它收起来。

v1.8.1 之前这一步藏在「长按标题 1.5 秒」里——那是个调试入口，用户永远找不到，
等于功能不存在。现在球分两种：琥珀色「学」是给用户的学习球，蓝色「检」是给排查用的
探测器（点一下跑一遍识别，能 dump 节点树），两者不会同时出现。

- **只学读得出字的东西**：控件 id > 内容描述 > 文字。id 最稳，跨版本还在；
  文案会随活动改，但至少是当下这一版能用的。
- **纯图标不学**。实测过一个只有自绘叉号的弹窗，它在无障碍树里是这样一行：
  `View | id='' | text='' | desc='' | [1155,1392][1305,1542] | clickable`——
  一个字段都没有。这种只能靠几何位置猜，而内容页右上角的「分类」「扫一扫」
  跟它长得一模一样，学出来的规则会到处误点。点它会明确告诉你「读不出文字，暂时学不了」。
- **目标必须自身可点**。这条是被真机教出来的：一开始按「面积最小的包含节点」选，
  结果用户戳叉号时选中的是手指底下的标题「会员特惠」（叉号没标签所以不在候选里），
  生成 `when:会员特惠 → action:会员特惠`，执行时去点一段不可点的文字，
  `Access.click` 顺着父链找到可点的卡片——一点就跑到了广告落地页。
- **学完立刻验证**：规则写完立即重载，下一次轮询（1 秒内）就会命中并关掉那个弹窗，
  用户当场看到结果，不用等下次打开。
- **能看、能复制、也能删**：「规则管理」顶部显示「已学会 N 条」，点开逐条查看，
  点一条可以「复制」成一行 `包名 | 应用名 | when | action`，一条规则一个字段不少；
  「复制全部」一次性导出。学来的规则单独存一层，不动你手写的自定义规则。
- **复制是为了回流**：学出来只在你手机上生效，别人遇到同一个弹窗还得重新学一遍。
  复制出来粘到问卷里，开发者就能把它并进公共库，下个版本所有人都能直接用。
- 学来的规则存成逐行文本（`TaughtRulesStore`），不是 JSON：JVM 单测里 android.jar 的
  `org.json` 是空壳，方法一调就抛 `not mocked`，存 JSON 的话去重、上限、转义
  这些最容易错的逻辑一行都测不了。

## v1.7.2 做了什么：把现场直接送到开发者手上

v1.7.1 让「导出诊断」说得清了，但没说清**发给谁**。系统分享面板里列出来的是
微信好友和群——对方得先加开发者好友才发得出来，而「装完没用」的人恰恰不会去加好友。

- 首页入口卡新增「**问题反馈**」：点一下先把精简版现场（机型 / 系统 / 权限 /
  最近 30 条记录）写进剪贴板，再弹窗问「要不要跳到腾讯问卷」，同意才跳。
- 顺序是**先复制、后跳转**，不能反：用户到问卷那一步才想起「记录在哪」就晚了，
  而他一个人在手机上，也没法一边填表一边回 App 往回翻。
- **跳出去之前必须问**：离开 App 打开第三方网页得他自己点头。
- 「导出诊断」保留原样，仍走系统分享，完整记录留给愿意配合的人。
- 反馈文本**只带最近 30 条**，并在小标题里写清「共 N 条」——截断了却不说，
  比不截断更误导。

## v1.7.1 做了什么：让别人看得懂你手机上的现场

v1.7.0 之后最难处理的一类反馈是「装了、权限也给了，但一个广告都不跳」。
手里只有一张首页截图，里面没有机型、ROM、三项权限、微窗状态、规则条数——
每缺一项，排查就多一轮往返。

- **无障碍判定拆成三态**：已连接 / 授权还在但服务没连上 / 未开启。
  小米系上最常见的故障就是「系统面板显示开着、进程早被杀掉」，以前这种情况
  首页照样是绿色「服务运行中」，用户和开发者看同一张截图都会以为正常。
  现在中间态直接写「**授权还在，服务没连上**」，点按钮回到系统设置关掉再打开。
- **「导出」改成「导出诊断」**：在运行记录前面加一段环境——机型 / 系统版本 /
  ROM / 无障碍三态 / 通知·悬浮窗·电池 / 微窗是否挂上 / 四个开关 / 规则条数 /
  上次连上与上次加载规则的时间。仍然**不联网、不写文件、不要新权限**，
  拼好的文本交给系统分享，发到哪由用户自己决定。
- 查不到的项一律写「读不到」，**不给默认值**——诊断工具把「查询失败」显示成
  「一切正常」，比没有诊断更坏。

## v1.7.0 做了什么：先回答「现在有没有在保护我」

老首页上五个块的视觉重量几乎一样：状态卡、四个开关、「规则管理」按钮、十行等宽日志、
一段提示语。眼睛没有落点；而「通知权限没开」这种真正会让功能失效的问题，被塞在
一行 12sp 小字里，长到要换行。

现在的结构：

- **状态卡置顶**：左边一句话说状态，右边 **40sp 数字**（今日已跳过 N 次）。
  出问题时数字的位置换成实心按钮（`去修复` / `重新开启`）——一次只让用户处理一件事。
- **三项后台权限变成三个小圆点**（通知 / 悬浮窗 / 电池）：正常是灰绿，缺哪项那个点
  变琥珀，点一下直接跳到对应系统设置。替换掉原来那行又长又挤的警告文字。
- **四个开关加图标底**、行高统一 62dp；总开关关闭时下面三项一起变淡并失能，
  避免「总开关关了但三个子项还亮着」的错觉。
- **「规则管理 / 运行记录」从按钮改成列表行**，和开关共用一套视觉。
- **十行等宽日志移出首页**，改成独立的记录页：按天分组、按应用命名，
  绿 / 琥珀 / 灰区分「跳过 / 拦截 / 没找到」，右上角「导出诊断」或长按任意一行。

真机（Redmi 24122RKC7C / Android 17 / HyperOS 4.0.3）逐状态截图确认了四种画面：
正常（服务运行中 · 49 次）、无障碍被系统关闭（琥珀卡 + 重新开启）、总开关关闭
（灰卡 + 三行变淡失能）、记录页（圆角与分隔线在分组边界正确）。

**这一版只动界面，判定逻辑与 v1.6.0 完全一致**——没有新增拦截条件，也没有放宽任何一条。
开关的默认值也未变（除了「自动学习」在 v1.6.0 已经改成默认开）。

## v1.6.0 做了什么：跳过按钮根本没有文字

### 一、根因不是阈值，是证据类型

有一类开屏广告从来没被跳过过。dump 出来整页只有两个可点节点：

```
View     clk=true 150x150 @[60,2326]   ← 跳过
TextView clk=true 120x53  @[75,2517]   ← 「广告」标签
```

两个节点的 `text` / `content-desc` / `resource-id` **全是空**——「跳过」两个字是
用 Canvas 画上去的。关键词匹配永远命中不了，调阈值也救不回来。

### 二、形状 + 强标记，两个都成立才点

- **形状**（`engine/DrawSkip.kt`，纯函数）：长宽比 ≥ 0.70、短边在屏幕短边的 4%~20%、
  水平中心落在左右各 32% 内、避开状态栏与导航条。那条 120x53 的「广告」标签因为
  长宽比 2.26 被排除掉了。
- **强标记（刹车）**：`splash` 类控件 id、`NativeVideoAd` / `AdView` 描述、
  「向上滑动 / 跳转至详情页 / 点击到落地页」这类开屏模板文案，至少命中一条。
  形状是会撞的（视频 App 主界面也有 150x150 的发布按钮），强标记才是唯一的保险。
- 三条前置：开屏窗口 6 秒内、当前页不是内容页、这一轮没点过。

真机连续 5 次冷启动，5 次跳过成功，其中 3 次走的就是这套自绘判据，命中的
`Rect(60,2326-210,2476)` 与 dump 的位置逐像素一致。

### 三、顺带把界面和记录再收一轮

- 开关从 8 个减到 4 个：删掉「严格档 / 拦截后弹提示 / 对全部应用生效 / 自动学习」，
  值固定为默认（自动学习默认改成**开**，否则新用户直接少了这条能力）；
  删掉整张「规则来源」卡片——远程同步本来就是自动跑的。
- 记录不再刷噪音：「规则已加载」「无障碍已连接」在界面过滤（导出仍完整）；
  「未找到跳过按钮」只在**真的见过广告页**时才记；「取不到界面」降级进 logcat。

单测从 130 条加到 142 条，A–G 真机回归 8/0。

## v1.4.0 / v1.5.x 做了什么：换证据，顺便下架测试开关

### 一、撤销按钮曾经等于没做

v1.3.11 的撤销通知用的是 `IMPORTANCE_LOW`。真机实测发现：Android 17 把它归进
`Aggregate_SilentSection`，**uiautomator 的节点树里连「撤销」这个节点都不存在**——
功能写了，用户看不到。

改成 `IMPORTANCE_DEFAULT` + 静音 + 新渠道 `adskip_guard_v2`，并把「点通知本体」
也接成撤销（正文写「点此撤销」）当第二道保险。

### 二、判定换证据（R4–R8）

- **R4 输入溯源**：`TYPE_VIEW_CLICKED` → `InputTrace`。全屏点击（覆盖 > 85%）
  不作否决，否则点击型广告会整类从「拦」变成「不拦」；自家点击按 600ms 过滤，
  实测日志里是 `ignored=self 148ms`，一次自动跳过不会被误当成用户点击。
- **R5 广告指纹**：SDK 类名前缀 + 控件 id **分段边界**匹配（不裸匹配 `ad_`，
  否则会命中 `download_` `loading_`）。
- **R6 两档处置**：`Tier(HIGH/LOW) × Mode(COMPAT/STRICT/SHADOW)`，默认 COMPAT。
- **R7** 应用商店不再无条件拦：要求「看到广告指纹」或「冷启动未进正片且不是用户点的」。
- **R8 80ms 快按**：前提是已经确认前台落在落地页上，否则宁可不按；
  relaunch 超时从 1.6s 收到 1.2s。
- **R10 配对熔断**：按（来源, 目的地）配对计数——同一对撤销两次锁 30 分钟，
  熔断期内再撤销锁 24 小时。

### 三、三个预防实验（v1.5.0，默认全关）

触摸屏蔽层（`TYPE_ACCESSIBILITY_OVERLAY` 吃触摸，最长 3 秒，右下角留解除入口）、
摇一摇前置（只判「冲击 + 反向回弹」且必须有广告指纹）、入口证据（首帧 Activity
与 launcher 比对，只记日志）。代码留着，界面上不摆。

v1.5.1 把界面上的测试与实验开关全部撤掉：探测器改成**长按标题 1.5 秒**进入，
影子模式与两个实验开关下架（`Prefs` 保留、默认关），「规则管理」改成整行。

## v1.3.11 做了什么

### 拦错了可以撤销（R3）

防跳转是**事后补救**：它看到「来源像广告 → 落地很快」就按返回，但看不到用户
到底点了什么。判错的代价是「App 打不开」，用户能做的只有再点一次——再判错，
再弹一次。

现在每次**真的动手**之后弹一条提示（`GuardNotice`）：

```
已拦截一次广告跳转
从 番茄小说 跳到了 淘宝，已自动返回          [撤销] [不再提示]
```

- 渠道 `adskip_guard_v1`，`IMPORTANCE_LOW`：无声、不抬头、不上锁屏；
  15 秒后自动消失，所有提示共用一个 id —— 连着拦三次只留一条。
- 点「撤销」：打开那个 App + **30 分钟内不再拦它**。
  30 分钟比自动熔断（连拦三次 → 5 分钟）长一个量级，因为撤销是用户
  **明确表态**，不是推断。
- **只能打开它的首页**：无障碍看不到 Intent，我们从来不知道用户原本要去
  落地页的哪一页。所以提示文案只写「已自动返回」，不承诺「回到原来那页」。
- 设置里有「拦截后弹提示（可撤销）」开关，关掉不影响防跳转。

顺带修了一处早就存在的问题：`share.sh` 里广告测试台写的是「19 个样本」，
实际是 22 个（15 种开屏 + 1 陷阱 + 1 对照组 + 1 弹窗 + 4 个反例），
ZIP 内的文件名一并改正。

验证：JVM 单测 **96/96**（新增 3 条：撤销熔断的时长与范围）；Lint **0 error / 30 warning**。
**未做真机回归**：通知与广播在 HyperOS 上的表现必须实测（渠道被关、后台启动 Activity 被限都有前科）。

## v1.3.10 做了什么

按 [`docs/防跳转-实施方案.md`](docs/防跳转-实施方案.md) 的顺序做的第一批：**先把分类收敛，再修 bug，最后把度量铺上**。
这一版里只有 R1 会改变实际行为，另外两项是结构与观测。

### 一、R9：「一个包是什么身份」只在一个地方回答

同一个包在这个项目里四次因为「两份名单各说各话、结果取决于 if 顺序」出事故：

| 版本 | 事故 |
|---|---|
| v1.3.4 | `isBlocked` 提前 return，来源链断掉，dt 全算错 |
| v1.3.4 | `contentPage` 统计放在规则命中之后，闸门永久失效 |
| v1.3.7 | 安装器被写进 `STORES`，装 APK 必被弹回 |
| v1.3.8 | 负一屏在扫描链的排除名单里，判定链读不到，拼多多连拦 5 次 |

现在 `AppLists.roles(pkg)` 返回一个包的**全部身份**（`SHELL` / `SYSTEM_UI` / `STORE` /
`LANDING` / `CONTENT` / `USER_DRIVEN` / `AD_PRONE` / `INERT` / `BROWSER`），
`hasRole()` 与它同源。扫描排除名单 `NEVER_SCAN` 改成由 `SHELL ∪ SYSTEM_UI ∪ INERT`
**派生**，往任何一份名单里加东西都会自动同步过去——再没有「只在一个环节生效」的可能。

三组语义互斥的角色（外壳 / 系统 UI / 商店）两两不相交，由单测断言，不靠 if 顺序。

### 二、R1：systemui 里的「最近任务 / 通知栏」算用户切页

旧代码 `pkg == "com.android.systemui"` 直接 return，来源上下文原样留着。于是
「在番茄小说里按最近任务 → 点淘宝」会被判成「番茄还在开屏、用户 1 秒后就到了淘宝」
→ 弹回。现在按 `className` 区分：

| 类名 | 处理 |
|---|---|
| `recents` / `overview` / `notificationshade` / `qs.` / `globalscreen` | 用户切页 → 清空来源 |
| `HeadsUpNotificationView` 等通知本体 | 不动（否则正在播广告时来条通知就漏拦） |
| `statusbar` | **不动**（与建议报告不同：heads-up 的容器就住在 statusbar 包里） |
| 拿不到类名（轮询路径） | 不动，保持 v1.3.9 行为 |

回滚开关：`GuardDecision.GUARD_SYSTEMUI_AS_USER_SURFACE`。

### 三、R2：拦截后回访记录 + 影子模式 + 结构化日志

判定链给出的是一组**推断**（来源像不像在放广告）。这版补了一个事实：
**被拦之后 10 秒内用户又自己点回去**，那这次拦截十有八九是错的。

- `InterceptLedger`：内存环形 5 条，命中就写一行「拦截后 6s 又回到 taobao，可能拦错了」。
  自家 relaunch 不算回访——那是拦截成功。
- 影子模式（设置里的「只记录不拦截」）：判定照跑，但不动手、**也不记任何账**。
  它绝不能更新 `lastBackAt` / `restoringPkg` / `RepeatGuard`，否则跑出来的不是
  「现行为」而是「现行为 + 影子污染」，拿它定阈值等于用错数据。
- 结构化日志：`guard ctx dest=… origin=… dt=… cold=… splash=… settled=… watched=… mode=… -> BACK|KEEP`。
  旧 `guard pkg=` 行格式不动，`test_guard.sh` 依赖它。

验证：JVM 单测 **93/93**（新增 19 条：角色互斥 4、systemui 类名 6、影子处置 3、回访账本 6）；
Lint **0 error / 30 warning**（无 NewApi）。

## v1.3.8 修了什么

### 一、从负一屏点开拼多多 / 美团，被反复弹回去

用户反馈原话：「拼多多多次拦截，美团也拦」。v1.3.7 的日志：

```
12:33:14  拦截跳转 pinduoduo：像广告跳转（来源 com.miui.personalassistant，1331ms，cold=true splash=true）
12:33:13  已从 pinduoduo 退出（该页会吞返回键）
12:33:09  拦截跳转 pinduoduo：像广告跳转（来源 com.miui.personalassistant，1226ms，cold=true splash=true）
12:33:08  已从 pinduoduo 退出（该页会吞返回键）
12:33:05  拦截跳转 pinduoduo：像广告跳转（来源 com.miui.personalassistant，1249ms，cold=true splash=true）
12:33:04  已从 pinduoduo 退出（该页会吞返回键）
12:32:53  拦截跳转 meituan：像广告跳转（来源 miui.systemui.plugin，128ms，cold=true splash=false）
```

一分钟内连拦五次，用户点一次被弹回一次。

**根因**：`com.miui.personalassistant`（负一屏「智能助理」）和
`miui.systemui.plugin`（控制中心/通知栏的插件进程）被当成了「跳转来源 App」。

它们天然满足「像广告」的三个条件，而且是**结构性地**满足：

| 判据 | 为什么恒为真 |
|---|---|
| `originCold = true` | `calcCold()` 对 passThrough 包返回 true —— 它们本来就不是 App |
| `originSettled = false` | 扫描链压根不扫它们，永远不会「进入正片」 |
| `dt` 很短（1.3 秒 / 128ms） | 用户点完图标，目标 App 几乎立刻就冷启动出来了 |

三个条件凑齐，`destIsLanding && originCold && !originSettled && dt <= 2500ms`
就成立 —— 这正是摇一摇广告的判据。

更糟的是**自激**：拦截之后 `restoringPkg` 会把负一屏重新标记成
「仍在开屏期」（`forceWatched = true`），用户再点一次时 `splash` 直接变成 true，
时间窗从 2.5 秒放宽到 8 秒，于是越拦越容易拦。

**这已经是同一个错误在这个项目里第四次出现**：名单只在一条链上生效。
前三次分别是 `isBlocked` 让被拦包当不了来源、`contentPage` 统计放在规则命中之后、
以及 v1.3.7 的安装器被写进 `STORES`。这三个包早就在扫描链的 `NEVER_SCAN` 里，
但 `JumpGuard` 的判定链读不到那份名单。

### 二、四层修复（任何一层单独都能挡住）

1. **`AppLists.SHELL`：系统外壳名单，两条链共用。**
   桌面 / 负一屏 / 控制中心插件 / 语音助手统一当「用户找 App 的地方」，
   命中即 `reset()` 清空判定上下文，不参与跳转判定。
   覆盖小米、华为、荣耀、OPPO、vivo、三星、原生桌面与各自负一屏，
   另有 `personalassistant` / `assistantscreen` / `voiceassist` / `launcher`
   等包名特征兜底，小众 ROM 也能命中。

   注意它和 `SYSTEM_UI`（安装器/权限弹窗）**处理方式必须不同**：
   安装器是「透明层」——它盖在真实 App 上面，不能清空来源上下文；
   外壳是「桌面」——用户在这里时上一个 App 的上下文已经彻底失效。

2. **`GuardDecision.MIN_DWELL_MS = 500`：在来源 App 里待不到半秒的「跳转」直接放过。**
   摇一摇最快也要 1 秒以上（打开 → 广告渲染 → 摇 → 落地）。
   128 毫秒只可能是切换动画的中间帧。

3. **`GuardDecision.RepeatGuard`：重复拦截熔断。**
   1 分钟内同一个目的地被拦到第 3 次，就认定「用户确实想进去」，
   5 分钟内不再拦它。名单再全也总有想不到的系统入口（各 ROM 负一屏、
   桌面小组件、车机投屏、语音助手），这是最后一道保险。
   熔断状态**不会**被「回到桌面」清掉——它记的是用户意图，跨桌面依然有效。

4. **系统外壳不再起开屏监测**（`isPassThrough` 增加 `isShell`），
   少扫一堆全是图标的界面树，也省电。

### 三、验证

- JVM 单元测试 **74/74**（当时 69 条，其中三条是上面日志的原文时序）
- 真机 Redmi 24122RKC7C / **Android 17 / HyperOS 4.0.3** 实测：
  从语音助手入口点开拼多多，日志确认
  `guard skip pkg=com.miui.voiceassist 系统外壳…` → `origin=null -> KEEP 没有来源 App`，不再拦截。

## v1.3.7 修了什么

### 一、用 MT 管理器装 APK，安装界面一弹出来就被弹回去

日志：

```
09:55:37  拦截跳转 packageinstaller：像广告跳转（来源 bin.mt.plus，246ms，cold=true splash=true）
09:55:40  已从 packageinstaller 退出（该页会吞返回键）
```

根因很具体：`com.miui.packageinstaller` 被写进了 `STORES`（应用商店名单），
而 `STORES` 是唯一「不限来源」的拦截目标 —— 也就是说，**系统安装器被当成了应用商店**。
用户每装一次 APK，安装界面刚出来就被判成广告跳转、立刻按返回。

安装器和商店是两回事：商店被 App 拉起九成是误触广告，该拦；安装器只会在用户
自己点 APK 时出现，是明确的用户意图。

修法：把安装器从 `STORES` 移出，新建 `AppLists.SYSTEM_UI` 白名单
（安装器 / 权限弹窗 / 分享面板 / 文件选择器 / 系统设置），并且**在 JumpGuard
判定链的最前面直接放行**。之所以要单独一份名单，是因为 `NEVER_SCAN` 只作用于
扫描链，判定链根本读不到它 —— 这个项目已经因为「名单只在一个环节生效」栽过三次。

真机验证（同一台设备，点 APK 触发系统安装界面）：

```
前台: com.miui.packageinstaller/com.miui.packageInstaller.ui.InstallPrepareAlertActivity
日志: guard skip pkg=com.miui.packageinstaller 系统 UI 容器（安装器/权限/分享/选文件），不参与跳转判定
```

没有任何「拦截跳转」记录，安装界面正常停留。

### 二、长时间运行后「跳过变慢、甚至不跳」

日志里的证据是一夜之间十几次冻结，最长一次 4698 秒：

```
03:34:18  后台被系统冻结 4698s
05:06:59  后台被系统冻结 3753s
06:05:24  后台被系统冻结 3505s
```

这类慢性退化没有单一断点，是进程内状态在累积（节点引用、点击记录表、
规则解析结果、日志队列）。所以做了两件事：

**1）定时重启（默认 6 小时）**
`App` 记录进程启动时刻，`KeepAliveService` 每 60 秒检查运行时长，
到点先写日志、清 `cacheDir`，再重启进程（约 2 秒）。
用 `elapsedRealtime` 计算，含深度睡眠 —— 手机放一夜也算运行时长，
因为休眠期间进程同样在老化。

6 小时是折中：一天最多重启两三次，用户几乎察觉不到，又能保证退化不会拖到被察觉。
可在 `Prefs.restartHours` 调整，设为 0 关闭。

**2）失联自愈（应急）**

补上了一个此前完全无人看守的死角。轮询器原来是这一行：

```kotlin
val pkg = runCatching { activePackage() }.getOrNull() ?: return@post
```

`rootInActiveWindow` 返回 null 时直接 return —— 没有统计、没有检测、没有恢复。
此时事件通道、轮询、扫描三条链**一起静默**：进程活着、无障碍也 bound 着，
但什么都发现不了。而 `KeepAliveService` 的 `instance != null` 判据恰好把它
当成健康状态，所以永远不会自愈，用户只能手动重启。

现在连续 60 秒拿不到活动窗口就判定服务已哑，交给 `KeepAliveService` 重启进程。
两条路径（定时 / 应急）共用 15 分钟冷却，避免互相打架。

## v1.3.6 修了什么

### 番茄小说的「书页退回书架」：元凶是我们自己点的

v1.3.5 以为已经修好了，用户回来说**还在退**。这次日志给了铁证，不需要再猜：

```
14:42:31  跳过 com.dragon.read · 点击关闭广告并退出小说（规则 关闭广告）
14:42:35  跳过 com.dragon.read · 点击关闭广告并退出小说（规则 关闭广告）
14:42:39  跳过 com.dragon.read · 点击关闭广告并退出小说（规则 关闭广告）
14:42:44  跳过 com.dragon.read · 点击关闭广告并退出小说（规则 关闭广告）
14:42:48  跳过 com.dragon.read · 点击关闭广告并退出小说（规则 关闭广告）
```

阅读页上有个节点的无障碍描述就是「**点击关闭广告并退出小说**」。通用规则词「关闭广告」按
「包含」匹配命中它，秒跳就点下去了——`ReaderActivity` 被 finish，用户看到的就是退回书架。
每 4 秒点一次，用户每次重新翻回书页又被打回书架。

根因在 `SafeWords.isUnsafe()` 的判断顺序：

```kotlin
if (AD_TOKEN.containsMatchIn(text)) return false   // ← 含「关闭广告」直接放行
return UI_WORD.containsMatchIn(text)               // ← 「退出」这一条永远走不到
```

「命中广告词就放行」是个错误的短路：一条文案**同时**含广告词和退出语义时，它不是跳过按钮，
而是「关闭广告（顺便退出）」这类描述性文案。

修法（四层，逐层收窄）：

| 层 | 做法 |
|---|---|
| 1. 否决词优先 | 新增 `VETO_WORD`（退出 / 返回 / 书架 / 目录 / 上一页 / 下一页 / exit / back / quit / leave），**先判否决再谈放行** |
| 2. 用完整文案判 | 安全判断原来吃的是 `Access.label()`，而它会 `take(14)` 截断。真实节点的文案 11 个字刚好过线，但更长的就会被切掉危险动词。新增 `Access.fullLabel()`，安全判断一律用它 |
| 3. text 与描述分别判 | 番茄那个节点是「文字为空、只有 contentDescription」。有的 App 反过来。只判一个字段就会漏一半 |
| 4. 误点熔断 | 语义只能挡已知形态。再加一层不看语义只看行为：**同一 App 的同一块区域 20 秒内被点第 3 次，就说明认错了控件**，停手 60 秒并记一条日志 |

顺带修掉一个一直是死的闸门：`ruleHits` 里原本写 `label.length > 20 → 跳过`，而 `label`
已经被截断到 14 —— 这个条件**永远不成立**，当年为 QQ 那条 GitHub 通知加的防护其实从未生效过。

### 永久回归样本

测试台新增第 16 个形态，节点和真实抓到的一模一样（文字为空、`contentDescription` 为
「点击关闭广告并退出小说」、右上角、36dp）：

- 关掉否决词的对照组：`❌ 点了退出按钮(exit=1) hit=... label=点击关闭广告并退出小说 how=规则 关闭广告`
- 修好之后：`✅ 没点退出按钮`

日志与用户手机上的**一字不差**，所以这个 bug 以后不可能再悄悄回来。

### 一个要提醒的点

排查时发现用户把「**跳过开屏广告**」开关关掉了（「自动学习」也是关的）。这两个开关都关着时，
`onForegroundChanged` 在第一行就 return，整条开屏扫描链不运行——所以那段时间日志里
只剩「防跳转」的记录，开屏相关一条都没有。如果你是为了止住弹回才关的，现在可以重新打开。

## v1.3.5 修了什么

### 小窗里看小说，翻着翻着回到书架

用户报：**游戏全屏 + 番茄小说悬浮小窗**，看着看着书页（`ReaderActivity`）退回书架（`MainFragmentActivity`），连看到第几章都丢了。桌面直接打开、后台切换回来也会复现。

这不是「判定错了一次」那么简单，是两个结构缺口叠在一起：

| 缺口 | 说明 |
|---|---|
| **不认识多窗口** | 小窗 / 分屏下两块界面同时可见，前台包名会在两个 App 之间**反复横跳**。旧代码把每一次横跳都当成「换了一次 App」去判定，把「切窗口」当成了「跳转」 |
| **`relaunch` 会重置任务栈** | 兜底第 2 级用 `FLAG_ACTIVITY_RESET_TASK_IF_NEEDED` 拉起来源 App。多窗口下任务栈会被系统重新组织，根 Intent 比对**经常判成不一致** → 任务栈整体重置 → 栈顶回到启动 Activity，也就是书架 |

修法：

- **识别多窗口**：2 秒内出现 `A → B → A` 的往返就判定「两块界面同时可见」，整体退出防跳转判定（判据是纯函数，`GuardDecision.isMultiWindow`，有单测）。真实的广告跳转是**单向**的，不会两秒内自己跳回来，所以不会挡住该拦的广告。
- **`relaunch` 去掉 `RESET_TASK_IF_NEEDED`**：只带 `NEW_TASK`。任务栈存在就整体带到前台、**栈顶保留**；任务栈被系统回收时等价于新建，效果相同。不会有任何场景因此变差。

### 出事之后查不到日志

这两个投诉都发生在几小时前，等我去取 `adb logcat` 时环形缓冲早已滚掉（HyperOS 上甚至会被整段清空），只剩代码可查。根因是「最近记录」只存在内存里，进程一被杀就归零。

- **记录落盘**：每条记录异步写入 `filesDir/skiplog.txt`（保留最近 800 条），进程重启、手机重启后自动载回。
- **长按导出诊断**：记录页右上角「导出诊断」，或长按任意一行。会先拼一段环境信息（机型、ROM、三态无障碍、三项权限、规则条数），再接完整记录，通过系统分享发出来——不用连电脑、不用 adb。
- **一键反馈**：首页「问题反馈」会先把精简版诊断复制到剪贴板，弹窗确认后再跳到腾讯问卷，粘在第 2 题即可。对方不需要加好友、不需要配邮箱。

### 关于「评论区打开没网络，刷新后正常」

结论：**与本应用无关**，它没有任何能力影响别的 App 的网络。详见下节。

## 秒跳会干扰别的 App 联网吗

不会。可以从三个层面核对：

**1. 权限层面**，只申请了 `INTERNET` 和 `ACCESS_NETWORK_STATE`（只读网络状态），没有 `VpnService`、没有 `CHANGE_NETWORK_STATE`、没有代理相关权限，也没有任何常驻的连接。

**2. 代码层面**，整个项目**只有一处**网络调用：`net/RemoteRules.kt` 里的规则同步，HTTPS GET 一份 JSON（约 61 KB，支持 ETag 增量、gzip、失败自动回退上一份缓存）。没有自建服务器、没有上报、没有埋点、不监听端口。

**3. 实测流量**（Redmi 24122RKC7C，同一个统计周期）：

| 应用 | 接收 | 发送 |
|---|---|---|
| 秒跳 | **0.05 MB / 78 个包** | **0.01 MB / 77 个包** |
| 番茄小说 | 24.61 MB / 46,145 个包 | 15.66 MB / 41,885 个包 |

78 个包基本就是同步一次规则的量级。这个数量级不可能对别的 App 联网造成任何影响。

番茄小说评论区「打开空白、刷新就正常」是它自己的 H5 容器首次加载失败（评论区是 WebView），冷启动或后台恢复时更容易撞上。这类现象与无障碍服务无关——无障碍拿到的是界面节点快照，不碰网络栈。

### 这一版怎么验证的

- **单元测试 40 条**全绿（新增 6 条覆盖多窗口判据的边界：单向跳转不算、间隔过久不算、采样不足不算、空包名不算）
- 真机 `test_guard.sh` **8/8**、`test_variants.sh` **21/21**（原有能力未受影响）
- 真机实测多窗口保护生效：连续快切两个 App，日志出现 `guard multi-window pkg=... 多窗口/小窗，跳过判定`
- 落盘实测：`am force-stop` 强杀进程后重启，「最近记录」里半小时前的记录仍在

## v1.3.4 修了什么

这一版专门修「用户被莫名其妙弹回去」——用户报了两次，**两次都不可复制、无法稳定复现**，所以除了逐条审查回退代码，还把判定抽成纯函数、补了 34 条单元测试来长期守住。

| 现象 | 根因 | 修法 |
|---|---|---|
| NFC 打开支付宝被弹回 | 支付宝同时在「用户主动打开」和「广告落地页」两份名单里，而落地页判断在前，豁免根本走不到 | 统一成一份**双向豁免**名单，优先级最高；支付宝移出落地页名单 |
| 番茄小说打开个人主页被弹回 | 番茄小说被当成「广告落地页」；且旧代码只认「包名变没变」的来源，番茄这类包**永远当不了来源**，判定用的是上一个 App 的陈旧时间戳 | 判定改成「**先快照旧来源 → 判定 → 再更新来源**」；同包切换压根不进判定；内容型 App 从落地页拆出来，门槛更高 |
| 正常内容页里点商品卡会被弹回 | 扫描器一旦命中规则就提前返回，`contentPage` 永远是 false →「来源已进正片」这个标记**永远置不上** | 页面统计与规则命中彻底解耦，无论规则有没有命中都算内容页特征 |
| 广告跳出去后连按返回、用户自己切走也退 | 第 1 级兜底按返回前**完全不复核前台** | 每一级动手前都复核前台；`relaunch` 不再用会改栈顶的 flag |
| 弹回来源 App 后第二次摇一摇不拦 | 弹回后来源被换成落地页，再切回来时「冷启动」信号已被消费 | 记下要弹回哪个 App，等它回到前台时重新武装成冷启动 |

另外修了一个**测试脚本自身的 bug**：Android 16 上 `dumpsys` 已不再输出 `mResumedActivity`，导致 `test_guard.sh` 的内容页场景一直静默跳过——「内容页闸门」这个关键机制其实从没被端到端验证过。现已改用 `topResumedActivity`。

## 快速开始

1. 到 **[最新 Release](https://github.com/jiangnan57/AdSkipper/releases/latest)** 下载 APK（或自行从源码构建），建议核对发布页给出的 **SHA-256**。
2. 安装后**先打开一次 App**，让进程与前台服务启动起来。
3. 系统设置 → 无障碍 → 找到「秒跳」→ 打开。
4. 按首页状态卡补齐三项授权：**通知权限**、**悬浮窗（显示在其他应用上层）**、**电池优化白名单 / 自启动**。三项缺一项，部分 ROM 上就会出现「开关开着但一个广告都不跳」。状态卡下那三个小圆点就是这三项——正常的偏灰绿，缺哪项哪个变琥珀，点一下直接进对应设置页。

> **重装 / 升级 APK 后**，HyperOS / MIUI 常常不会自动重连无障碍服务。表现是「设置里看着是开的，但完全没反应」——把该开关关掉再打开一次即可（有 USB 调试时也可重新 `settings put secure enabled_accessibility_services ...`）。

## 规则

五层合并，后者覆盖前者：`内置（res/raw/default_rules.json） → 远程缓存 → 自动学习 → 学弹窗 → 自定义（手写）`。

- **遇到关不掉的弹窗不用等规则更新**：首页「教它关弹窗」放出「学」球，切到那个 App，
  点一下球再点一下要关掉的按钮，当场生成一条规则并立即生效。见上文 v1.8.0 一节。
- 学来的规则在「规则管理」顶部能看能删，单独一层，不会动到手写的那份。
- 内置规则覆盖常见应用；远程规则可填任意返回 JSON 的 **https** 地址（明文 http 会被拒绝，因为规则本质是可执行的点击指令，中途篡改风险太高）。
- 兼容「李跳跳」社区规则格式（包名哈希数组），会在本机已安装应用里反查包名，未安装的规则不建立对象。
- 可选公共规则源来自 [Snoopy1866/LiTiaotiao-Custom-Rules](https://github.com/Snoopy1866/LiTiaotiao-Custom-Rules)，仅作为第三方数据源，权利归原作者，本项目与其无关联、也未获其认可。远程规则内容请自行审查。
- 规则语法、时序参数与排障实例见 [docs/DEV_NOTES.md](docs/DEV_NOTES.md)（**早期版本笔记，部分内容已过时**）。

## 从源码构建

需要 JDK 17、Android SDK 34（build-tools 33+）、Gradle 8.4；在 `local.properties` 里写 `sdk.dir=<你的 SDK 路径>`（该文件不入库）。

```bash
# Linux / macOS
./gradlew assembleDebug

# Windows
gradlew.bat assembleDebug
```

GitHub Actions（`.github/workflows/build.yml`）会在 push 时编译 debug 包并上传为 artifact，**不需要任何密钥**。

打 release 包需自备签名密钥，口令通过环境变量或 `local.properties` 提供（**绝不写入版本库**）：

```bash
ADSKIP_STORE_PASS=xxx ADSKIP_KEY_PASS=xxx ./gradlew assembleRelease
```

> 缺少密钥时 release 构建会直接报错，而 debug 构建不受影响。`keystore/`、`local.properties`、`dist/` 均已在 `.gitignore` 中排除。

## 测试

`adsample/` 是一个人造广告测试台，包含 **22 种样本**：多种开屏广告形态、内容页负向样本（验证不误点）、运营弹窗样本，以及一个「长得像跳过键但点了会退出阅读页」的陷阱样本（#16）。

```bash
bash test_variants.sh <adb 设备序列号>    # 广告形态：22/22
bash test_guard.sh   <adb 设备序列号>    # 防误跳八场景：8/8
```

回归需要 USB 调试、测试期间**独占前台**（不要同时打开其他 App），并且每次重装后重新绑定无障碍。另外首页的「跳过开屏广告」必须**开着**，否则开屏扫描链整个不运行，正向样本会全部判「未跳过」。

上一轮完整真机数据来自 **v1.7.0**（Redmi 24122RKC7C，**Android 17 / HyperOS 4.0.3**）：广告形态 **22/22**、防误跳八场景 **8/8**、JVM 单测 **142/142**、Lint 0 error；无障碍、通知、悬浮窗、电池白名单、待机分组（EXEMPTED）全绿，无崩溃、无权限拒绝。v1.4.0 / v1.5.0 / v1.5.1 / v1.6.0 / v1.7.0 每一版都重跑了 A–G 八场景并全部通过。

**仍未验证的**：R11 触摸屏蔽、R12 摇一摇前置在真实广告场景下的表现（这两个是默认关的实验项）；WebView 内部的点击派发；严格档长期运行的漏拦率；场景 G 依赖负一屏，adb 构造不出来，只能人工点。

名单与角色那 20 条不是测「某几个包名对不对」，而是测**集合之间的关系**：安装器必须被识别成系统 UI、且绝不能出现在 `STORES` 里；外壳 / 系统 UI / 商店三组两两不相交；扫描排除名单必须真的由角色派生。这个项目四次栽在「同一个包出现在两份名单里、或名单只在一个环节生效」，用断言把这类错误拦在编译期之后。

`test_guard.sh` 验证的是「该拦的拦住、不该拦的放过」：广告跳淘宝 / 跳商店要能自动退出，而用户自己点进淘宝、或在内容页正常使用后跳转时绝不能乱返回。

### 回退判定有单元测试

「什么时候该按返回」依赖一堆时序条件（来源是冷启动还是后台恢复、来源有没有扫到内容页、来源还在不在开屏期、距来源前台多久、距上次回退多久……），**真机上几乎无法稳定复现**——用户自己都说不清是哪一步触发的。

所以判定被抽成了纯函数 [`engine/GuardDecision.kt`](app/src/main/java/com/miaotiao/adskip/engine/GuardDecision.kt)（不 import 任何 `android.*`），配套 40 条 JVM 断言：

```bash
./gradlew testDebugUnitTest
```

覆盖的两条真实投诉（2026-11-07）：

- **NFC 打开支付宝时回退** —— 支付宝原本同时在「用户主动打开」和「广告落地页」两份名单里，落地页判断在前，豁免根本走不到。现在统一成一份双向豁免名单，优先级最高。
- **番茄小说打开个人主页时回退** —— 番茄小说原本被当成「广告落地页」，于是同包切页也被重判一次。现在同包切换压根不进判定。

CI 每次 push 都会跑这套测试，谁改了判定逻辑、谁动了名单，一跑就知道。

### 跳过词表也有单元测试

`SafeWords` 同样不依赖任何 `android.*`，所以「这条文案到底能不能点」也能在 JVM 上断言。
`SafeWordsTest` 用真实抓到过的无障碍文案做回归，第一条就是 v1.3.6 那个元凶：

```kotlin
assertTrue(SafeWords.isUnsafe("点击关闭广告并退出小说"))
assertFalse(SafeWords.isUnsafe("跳过 5s"))
assertFalse(SafeWords.isUnsafe("关闭广告"))
```

另外 `isVetoed()` 单独暴露「只判否决词」：已经确认是关闭控件的节点（比如只有一个 ✕、
描述写着「关闭」）走 `isUnsafe` 会被界面通用词拦掉，但含退出语义的仍然必须挡住。
这两条边界各有单测，改动词表时会立刻反映出来。

## 已知限制

1. 无 root 情况下无法零延迟拦截跳转，防跳转只能事后按返回；拦错了靠通知或通知栏撤销。
2. 自绘跳过按钮只在**开屏场景**能识别（靠形状 + 广告强标记）；页面里没有 `splash` 类 id、也没有开屏文案与广告 SDK 描述时，宁可放过不点。Android 14+ 的 `accessibilityDataSensitive` 会让金融、输入法等应用对无障碍不可见。
3. 通用规则（generic）中的 `popups` 不生效；应用级 `exclude` 字段被忽略，只认顶层 `defaults.exclude`。
4. 各家 ROM 的省电策略会静默解绑无障碍，必须完成上述四项授权。
5. 内置规则只是起点，App 版本差异很大，建议用自检探测器抓真实节点后自行补规则。
6. 未在多种机型 / 系统版本上做过系统性兼容测试。

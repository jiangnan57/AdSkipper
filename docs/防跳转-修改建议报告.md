# 防跳转 · 误拦治理修改建议报告

> 对象：秒跳 AdSkipper **v1.3.9**（versionCode 14）
> 依据：同目录源码静态审查（`dist/秒跳-AdSkipper-v1.3.9-20261123-896ce5a4.apk` 对应的源码）
> 日期：2026-11-25 ｜ 状态：**建议稿，未改任何代码**
> 说明：标 🔶 的条目是「需要真机/真实日志才能定论」，本文不把它们当结论。

---

## 0. 摘要

v1.3.9 已经把「名单漏了一个包」「if 顺序排错」这类事故修得差不多了。经代码审查，**残余误拦的主因不是规则不够多，而是判据的方向**：

> 现有信号全部在描述「来源 App 像不像在放广告」，
> 没有一条在描述「这次跳转和用户的手指之间有没有因果关系」。

因此本报告的修改建议分三类，优先级按「收益 ÷ 风险」排：

| 类别 | 内容 | 作用 |
|---|---|---|
| **止损** | 系统 UI 语义修正、撤销入口、回访指标、影子模式 | 不改判定，先把误拦的代价和可观测性补上 |
| **换证据** | 输入溯源、广告指纹、目的地入口证据 | 用正交事实替代「猜来源」 |
| **换处置** | 两档处置（高置信回退 / 低置信只提示）、relaunch 优先 | 让「判错」不再等于「页面丢失」 |

两条贯穿全文的设计约束（沿用项目既有原则）：

1. **代价不对称**：漏拦 = 多看两秒广告；误拦 = 用户打不开 App。所有新信号默认只能做**否决**。
2. **看不到证据的权重不许上线**：任何参与「确认」的信号，必须能在日志里一行说清。

## 1. 问题定义与度量口径

### 1.1 两类错误

| 错误 | 定义 | 用户感受 | 现状 |
|---|---|---|---|
| **漏拦（FN）** | 广告真的跳走了，没弹回 | 多看两秒广告 | 可接受 |
| **误拦（FP）** | 用户自己触发的跳转被弹回 | 打不开 App、页面/进度丢失 | 会卸载 |

本文的「降低误跳转」按**误拦**理解。若指的是 FN（广告没拦住），第 3 节的 R5（广告指纹）与 R12（传感器前置）同时覆盖。

### 1.2 可度量的指标（当前完全没有）

| 指标 | 定义 | 怎么算 | 用途 |
|---|---|---|---|
| **回访率** | 拦截后 10 秒内，用户又主动回到被拦的落地页 | 前台序列 + 拦截时间戳 | **误拦的代理指标**，纯本地可算 |
| **拦截次数 / 日** | 现有 `SkipLog` 已有 | 日志统计 | 基线 |
| **熔断触发次数** | `RepeatGuard` 已有 | 日志统计 | 近似「连拦」 |
| **影子回退数** | 影子模式下「本会回退」的次数 | 新增埋点 | 改动前的对照 |

> 回访率不是真值：用户可能真的想再进去看广告页。但它是最便宜、最接近真值的代理，且**方向安全**——只用来「少拦」，不用来「多拦」。

### 1.3 判定原则（建议写进代码注释）

> 新信号默认只能做**硬否决**。
> 要参与**确认**，必须能回答：这个信号为真时，用户主动跳转的概率是多少？答不出来就不许进 `originOk`。

## 2. 现状诊断（代码级）

### 2.1 判定实际用到的信号

| 信号 | 来源 | 性质 |
|---|---|---|
| 前台包名变了 | `TYPE_WINDOW_STATE_CHANGED` / 轮询 | ✅ 观测 |
| `dt`（在来源里待了多久） | 时间戳 | ✅ 观测 |
| 目的地 / 来源的名单分类 | `AppLists` 硬编码 | ⚠️ 推断 |
| `originCold` | `calcCold()` 启发式 | ⚠️ 推断 |
| `originShowingSplash` | `watched && !settled` | ⚠️ **否定证据** |
| 用户有没有点屏幕 | — | ❌ 完全缺失 |
| 目的地是怎么被拉起来的 | `e.className` 只写日志 | ❌ 未使用 |

`originShowingSplash` 是核心问题：它的语义是「我**没扫到**内容页」，不是「我**看到**广告在播」（[JumpGuard.kt L301](../app/src/main/java/com/miaotiao/adskip/service/JumpGuard.kt#L301)）。对首页加载慢、WebView 首页、或内容页判据不适配的 App，这个值在整个 8 秒窗口内恒为真。

### 2.2 四个具体缺陷

**D1｜系统 UI 早退但不清空来源（真实 bug）**

[JumpGuard.kt L188](../app/src/main/java/com/miaotiao/adskip/service/JumpGuard.kt#L188) 对 `com.android.systemui` 直接 `return`，不动 `originPkg`。而 `calcCold()` 因为 systemui 属于 `isPassThrough` 会返回 `true`（[SkipAccessibilityService.kt L620-L631](../app/src/main/java/com/miaotiao/adskip/service/SkipAccessibilityService.kt#L620-L631)、[L727-L731](../app/src/main/java/com/miaotiao/adskip/service/SkipAccessibilityService.kt#L727-L731)）。在「最近任务/通知栏由 systemui 承载」的 ROM 上：

```
用户冷启动 App A（watched、未 settle）
  → 上滑最近任务（systemui）
  → 点淘宝
  → origin 还是 A、cold=true、splash=true、dt 很小
  → 判定拦截 → 弹回
```

现有注释把 systemui 当「透明层」，理由是「跳去授权再返回要保留来源」。但**权限弹窗在 `permissioncontroller`、系统设置在 `settings`**，这两个都已经在 `SYSTEM_UI` 里了。systemui 的「最近任务 / 通知栏 / 下拉状态栏」本质是**用户操作层**，语义更接近 shell。

⚠️ 但不能一刀切：**悬浮通知（heads-up）也是 systemui**。如果每次它出现都 `reset()`，广告播放期间来一条通知就会把来源清掉 → 漏拦。所以必须按 `className` 区分（见 R1）。

**D2｜商店「不限来源」短路得太彻底**

[GuardDecision.kt L438-L443](../app/src/main/java/com/miaotiao/adskip/engine/GuardDecision.kt#L438-L466) 里 `c.destIsStore -> true`，连 `originSettled` 都不看。于是「打开 App → 弹版本更新 → 点立即更新」只要在 5 秒内发生就必被弹回，更新弹窗也一起没了。这条在「误触概率极高」的前提下是合理取舍，但**有了点击证据就可以既保留拦截又不误伤**。

**D3｜否决链里没有任何「必须存在的正面证据」**

[GuardDecision.kt L346-L466](../app/src/main/java/com/miaotiao/adskip/engine/GuardDecision.kt#L346-L466) 先排掉所有「确定不是」的情况，再看「像不像」。问题在于：除商店外，其他目的地都留了**降级窗口**（`WINDOW_UNWATCHED_MS`），也就是说「没有任何正面证据」也能回退。误拦的下界因此由「来源冷启动后 N 秒内用户会不会主动跳」决定，而这个概率在电商类 App 里并不低。

**D4｜同一个语义仍有两份实现**

`AppLists` 已集中了五份名单，但 `NEVER_SCAN` 还在 service 里（[SkipAccessibilityService.kt L69](../app/src/main/java/com/miaotiao/adskip/service/SkipAccessibilityService.kt#L69)），`isInUserBlocklist` 在 JumpGuard 里另算（[L452-L465](../app/src/main/java/com/miaotiao/adskip/service/JumpGuard.kt#L452-L465)）。前四次事故的共性「名单只在一条链上生效」只是从 4 处减到 2 处，没有从结构上消除。

### 2.3 处置动作本身的成本

| 环节 | 现状 | 用户感知 |
|---|---|---|
| 第 1 级返回 | 固定等 **400ms** 后才按（[L512-L531](../app/src/main/java/com/miaotiao/adskip/service/SkipAccessibilityService.kt#L512-L541)） | 广告页先完整显示 |
| 落地页吞返回键 | 1.6s 才 `relaunch` | 最多 **1.6 秒**广告 |
| 第 3 级 | `GLOBAL_ACTION_HOME` | 回桌面，上下文丢失 |
| 误拦后 | 无撤销入口，只能「再点一次」 | 反馈极隐晦 |

### 3.2 R1｜系统 UI 按 className 区分并失效来源

**问题**：D1。

**改法**

1. 在 `JumpGuard.onForeground` 里，`com.android.systemui` 不再无条件 `return`，而是看 `className`：

```kotlin
// 伪代码
if (pkg == "com.android.systemui") {
    if (isUserSurface(className)) {   // Recents / Overview / NotificationShade / StatusBar
        originPkg = null; originAt = 0; originCold = false
        originSettled = false; originWatched = false
        lastRealPkg = pkg
    }
    return   // 其他 systemui（heads-up / 音量条 / 电源菜单）维持现状
}
```

2. `isUserSurface` 用**正向匹配**，不要用「非 heads-up 即用户层」的反向写法：

```kotlin
private val USER_SURFACE = Regex(
    "(?i)recents|overview|notificationshade|statusbar|quicksettings|globalscreen"
)
```

3. `TYPE_WINDOW_STATE_CHANGED` 已经带 `e.className`（[L678](../app/src/main/java/com/miaotiao/adskip/service/SkipAccessibilityService.kt#L678) 已在日志里打），直接透传给 JumpGuard 即可；注意轮询路径没有 className，传 `null` 时保持旧行为（不为 null 才失效来源）。

**代价**：从「最近任务/通知栏」点开 App 不再拦（本来也不该拦）。heads-up 通知不会触发 reset。

**验收**：
- 单测：systemui + `RecentsActivity` → reset；systemui + `HeadsUpNotificationView` → 不动。
- 真机：冷启动 App A → 上滑最近任务 → 点淘宝，日志出现 `origin=null -> KEEP`。
- 现有场景 A-G 全部不回退（`test_guard.sh`）。

**回滚**：一个常量开关 `GUARD_SYSTEMUI_AS_USER_SURFACE`。

### 3.3 R2｜回访指标 + 影子模式

**问题**：1.2 的两个指标现在都没有；任何优化都无法证明有效。

**改法**

1. **拦截留痕**：每次 `backOffLanding` 记 `Intercept(destPkg, originPkg, at)`，只留最近 5 条。
2. **回访检测**：后续 `onForeground(pkg)` 里，若 `pkg == intercept.destPkg && now - intercept.at < 10_000`，且这次前台变化不是我们自己 `relaunch` 造成的（用 `restoringPkg` / `lastRelaunchAt` 排除）→ 记一条：

```
SkipLog.add("拦截后 ${n}s 用户又回到 ${dest}，可能拦错了")
```

3. **影子模式**：新增 `Prefs.guardShadow`。判定照跑、日志照写，但 `shouldBack` 时不执行任何动作，日志改用 `would_back` 前缀：

```kotlin
if (Prefs.guardShadow) {
    Log.d("AdSkip", "guard would_back pkg=$pkg ${verdict.reason}")
    SkipLog.add("【影子】本会拦截 ${pkg.substringAfterLast('.')}：${verdict.reason}")
    return
}
```

> 影子模式必须**连状态一起冻结**：不能设置 `restoringPkg`、不能更新 `lastBackAt`、不能动 `RepeatGuard`。否则「本会拦截」会污染下一次真实判定的 `cold` / 开屏期标记，影子跑的就不再是现行为。

4. 日志格式固定成可解析的一行（现有 `guard pkg=... -> ...` 已经够），新增字段追加在末尾，不要改动已有前缀——`test_guard.sh` 靠它。

**代价**：多几次 SharedPreferences / 环形日志写，可忽略。

**验收**：
- 影子模式下 `test_guard.sh` 场景 A/B 前台**不**变化，但日志出现 `would_back`。
- 人工制造一次误拦（点商品卡），日志出现「可能拦错了」。

**回滚**：开关默认关；不改任何判定分支。

### 3.4 R3｜撤销入口

**问题**：2.3 最后一行。误拦后用户唯一的出路是「再点一次」，靠 `RepeatGuard` 三次熔断，太隐晦。

**改法**

1. 拦截成功后发一条低优先级通知（渠道名「拦截提示」，静音、无横幅）：

```
已拦截一次广告跳转
淘宝 · 来自 番茄小说
[撤销，回到淘宝]   [不再提示]
```

2. 「撤销」→ `relaunch(destPkg)` + 对该 `(origin,dest)` 配对熔断 30 分钟 + `SkipLog` 记一笔「用户撤销」。
3. 通知用 `setTimeoutAfter(15_000)`，过期自动消失，不占通知栏。
4. 首页开关：`Prefs.guardUndoNotify`，默认开。

**依赖**：`POST_NOTIFICATIONS`（已在权限清单里）。

**风险**：通知渠道在部分 ROM 上被折叠；不影响主流程。

**验收**：拦截后通知出现；点撤销能回到落地页且 30 分钟内不再拦同一对。

### 3.5 R4｜输入溯源（首推）

**问题**：D3。用户自己在详情页点商品卡，和摇一摇落地，在时间线上完全重叠；唯一决定性区别是**有没有一次用户输入**。

**改法**

1. `accessibility_service_config.xml` 的 `accessibilityEventTypes` 增加 `typeViewClicked`（[当前只有 windowState/windowContent](../app/src/main/res/xml/accessibility_service_config.xml#L16)）。
   - 可选追加 `typeTouchInteractionStart|typeTouchInteractionEnd` 🔶待测：不保证所有 ROM 下发，且可能要求触摸探索模式。
2. `onAccessibilityEvent` 里新增分支，只记时间戳，**不取 source、不读节点**（避免 IPC）：

```kotlin
AccessibilityEvent.TYPE_VIEW_CLICKED -> {
    if (now - selfActionAt > 600L) {     // 排除我们自己的点击
        InputTrace.note(pkg, now)
    }
}
```

3. **必须排除自家动作**：`doScan` 里的 `Access.click` / `Access.tapAt`、`backOffLanding` 的返回、以及 `dispatchGesture` 都要更新 `selfActionAt`。否则一次自动跳过会造出一个假「用户点击」→ 后续 1.5 秒漏拦。
4. `GuardDecision.Context` 增加 `userInputAgoMs: Long`、`inputPkg: String?`；判定链在 ③ 之后加一条硬否决：

> 注意默认值：**没有输入时必须传 `Long.MAX_VALUE`**（表示「很久没点了」），不能传 0——0 会被判成「刚刚点过」，把整条防跳转全部否决掉。这是这类信号最容易写错的一行。

```kotlin
if (c.inputPkg == c.originPkg && c.userInputAgoMs in 0..1_500) {
    return keep("用户 ${c.userInputAgoMs}ms 前自己点了一下")
}
```

5. 日志里带上输入信息：`input=1200ms@pkg`。

**风险**

| 风险 | 缓解 |
|---|---|
| WebView / 自绘广告不派发 click | 只做否决，不做确认；漏拦方向安全 |
| 自家点击污染 | `selfActionAt` + 600ms 抑制窗 |
| 事件量增加（每次点击一条） | 回调里只写一个 Long，零分配 |
| `TYPE_TOUCH_INTERACTION` 不下发 🔶 | 先只用 `TYPE_VIEW_CLICKED`，探针验证后再加 |

**验收**：
- 单测：`inputPkg == origin && ago < 1500` → KEEP；`ago > 1500` → 走原判定。
- 真机：冷启动电商 App，2 秒内点一个商品卡 → 不弹回，日志出现「用户 xxx ms 前自己点了一下」。
- 反向：不点，摇一摇 → 仍然弹回。

### 3.6 R5｜广告指纹 `adSeenAt`

**问题**：`originShowingSplash` 是否定证据（D3）。树里本来就有 `viewIdResourceName`（`flagReportViewIds` 已开），扫描成本已付。

**改法**

1. `SplashScanner.pageStats` 增加指纹统计（一次遍历，零额外 IPC）：

```kotlin
// viewId / className 片段
tt_splash, ksad, gdt, pangle, csj, bd_ad, sigmob, mimo,
"ad_", "splash_", "skip_btn", "adskip", "ad_close",
"com.bytedance.sdk", "com.qq.e", "com.kwad", "com.baidu.mobads"
```

2. `Result` 增加 `adFingerprint: Boolean`（命中任一 + `strictAdPage`/`bigArea` 任一结构特征）。
3. `doScan` 里 `JumpGuard.noteAdSeen(pkg)`（仅当 `pkg == originPkg`）。
4. `JumpGuard` 存 `adSeenAt`，TTL 8 秒；`Context` 增加 `originAdSeenRecently`。
5. 判定按模式分两档（与 R6 的三档模式对齐）：

```kotlin
// 严格模式：收紧，用「看到广告」替代「没看到正片」→ 减误拦，可能增漏拦
c.destIsLanding -> c.originCold && !c.originSettled && c.originAdSeenRecently

// 兼容模式：保留现行为，指纹只做加分
c.destIsLanding -> c.originCold && !c.originSettled &&
    (c.originAdSeenRecently || c.originShowingSplash || c.dtMs <= WINDOW_UNWATCHED_MS)
```

**不要一步切换**：v1.4.0 先只把 `adfp=` 写进日志、判定不动，跑一周影子数据；确认「有指纹但被漏拦」的比例可接受之后，再把严格模式设为默认。严格模式下没有指纹的广告会漏拦——这是刻意的取舍（漏拦 < 误拦），兼容模式给不能接受漏拦的用户留着。

**风险**：指纹表靠人肉维护；漏命中 → 严格模式漏拦。缓解：指纹只做「加分项」，严格模式必须同时满足 `cold && !settled`；兼容模式随时可切回。

🔶 建表方法：debug 版打开 `SplashScanner.DEBUG_NODES`，跑 10 个主流开屏，收集 `id=` / `cls=`，再固化。

**验收**：日志出现 `adfp=true`；对拍 10 个 App 的开屏页，指纹命中率 ≥ 7/10。

### 3.7 R6｜两档处置（严格 / 兼容 / 影子）

**问题**：判定再准也有错的时候，而当前「错」的代价是页面丢失。

**改法**

1. `GuardDecision.Verdict` 增加 `tier: HIGH / LOW`：

```
HIGH = adfp + 无用户输入 + 目的地命中 + dt 在窗口内 + cold & !settled
LOW  = 其余所有当前会 BACK 的情况
```

2. 处置：

| 档 | 处理 |
|---|---|
| HIGH | 自动回退（现行为） |
| LOW（严格模式，默认） | **不回退**，只记日志 + 3 秒悬浮提示「疑似广告跳转，已保留」 |
| LOW（兼容模式） | 按现行为自动回退 |
| 影子模式 | 什么都不做，只记录 |

3. 首页给三档单选：`严格（推荐）/ 兼容 / 只记录`，映射到 `Prefs.guardMode`。

**为什么这是最值钱的一条**：它把「分类器不够准」从灾难降级为烦人，并自带标注数据（用户点不点「前往」）。

**风险**：用户会觉得「没以前跳得勤」。缓解：提示条要说明「这次拿不准，所以没动你的页面」。

**验收**：严格模式下，无广告指纹的跳转不再弹回；有指纹的仍然弹回。

---

### 3.8 R7｜商店分支加正面证据

**问题**：D2。

**改法**（依赖 R4/R5，所以排在 P1）

```kotlin
c.destIsStore ->
    c.originAdSeenRecently || (c.originCold && !c.originSettled && c.userInputAgoMs > 1_500)
```

即：要么有广告指纹，要么「冷启动 + 没进正片 + 用户没点」。这样「点更新」被点击证据挡掉，摇一摇拉商店仍然拦。

**验收**：真机「打开 App → 等更新弹窗 → 点更新」不弹回；「摇一摇拉商店」仍弹回。

---

### 3.9 R8｜处置时序：relaunch 优先 + 事件时刻快按

**问题**：2.3。现在 400ms 按返回、被吞掉后 1.6s 才拉起，用户看 1.6 秒广告。

**改法**

1. 窗口事件到达时（我们**刚**确知前台是落地页），立刻排一次 60~80ms 的返回，不等 400ms；400ms 那一路保留作兜底，每次动作前仍然复核前台包名。
2. 1.6s 的 `relaunch` 提前到 1.0s。
3. 可选（🔶待真机）：直接把「拉起原 App」作为第 1 级（~120ms），返回降为第 2 级。理由：`NEW_TASK` 不带 RESET 已能保留任务栈顶，比「按返回被欢迎页吃掉」更可靠。
   - 代价：落地页任务留在后台，用户下次从图标进可能看到那张券页。

**风险**：转场动画期间 `startActivity` 有竞态；必须在真机上确认不会把落地页又顶回来。

**验收**：场景 A 的可见广告时长从 ~1.6s 降到 < 400ms（用 120fps 录屏数帧）。

---

### 3.10 R9｜单一分类源 + 组合不变量测试

**问题**：D4。四次事故的共性不是「某个包名写错」，是「**一条 if 的顺序决定一切，而顺序会被人改**」。

**改法**

1. 引入 `AppRole` 枚举 + 唯一分类函数：

```kotlin
enum class AppRole { SHELL, SYSTEM_UI, BROWSER, STORE, LANDING, CONTENT, USER_DRIVEN, AD_PRONE }
fun classify(pkg: String): Set<AppRole>
```

`NEVER_SCAN` 从 `SHELL ∪ SYSTEM_UI ∪ {几个特例}` 派生；`isPassThrough`、`isShell`、`isStore` 全部改为查这一个函数。
2. **组合不变量测试**（判定是纯函数，17 个布尔量 2^17 = 131072 组，JVM 上 < 1 秒）：

```
∀ c: 任一硬否决为真 → KEEP
∀ c: 无正面证据 → KEEP（严格模式）
∀ c: destChanged=false → KEEP
∀ c: originIsShell → KEEP
```

3. **日志回放**：现有日志行已含全部 Context 字段，写一个解析器把 `guard pkg=... origin=... dt=...` 还原成 `Context`，把用户投诉的原文时序钉成回归用例（v1.3.8 已经手工做过三条，这里做成工具）。

**验收**：`./gradlew :app:testDebugUnitTest` 全绿；新增不变量测试 ≥ 4 条；回放用例 ≥ 10 条。

### 3.11 R10｜配对白名单学习（接 R2）

**问题**：`RepeatGuard` 是「同一目的地 1 分钟 3 次」熔断，粒度粗、不持久、不区分来源。

**改法**

1. 以 `(originPkg, destPkg)` 为键存统计：`intercepts`、`undoOrReturn`、`lastAt`，SharedPreferences 落盘，上限 200 对，30 天衰减。
2. `undoOrReturn ≥ 2` → 该配对熔断 30 分钟；再次触发 → 熔断 24 小时。
3. 只影响「拦不拦」，不影响任何名单。

**方向安全性**：只会让系统**少拦**，不会多拦。

**验收**：同一对连续两次被撤销后，第三次不拦。

### 3.12 R11｜触摸屏蔽层（实验，P2）

**问题**：现在所有「防」都是事后补救。点击型广告（点任意位置跳转）其实可以**不让它发生**。

**改法**

1. 广告指纹确认后，用 `TYPE_ACCESSIBILITY_OVERLAY` 加一层透明全屏 View（`FLAG_NOT_FOCUSABLE`，不加 `NOT_TOUCHABLE`），吃掉广告热区的触摸。
2. 跳过按钮两条路：
   - 优先 `ACTION_CLICK`（无障碍点击不经过触摸注入，不受覆盖层影响）；
   - 必须坐标点击时，先移除覆盖层 50ms 再注入（或按 `hit.rect` 四周摆 4 块矩形，留出按钮）。
3. 硬性约束：最多 3 秒；必须提供一个可见的「解除屏蔽」小按钮；物理返回键始终可用（覆盖层不能拦系统键）。

**风险（都要真机验证）**

| 风险 | 说明 |
|---|---|
| 挡自己的 `dispatchGesture` | 坐标点击会打在覆盖层上 → 必须临时移除 |
| 触发系统的「叠加层检测」 | 部分 ROM 在权限弹窗时禁用触摸 |
| 与手势导航冲突 | 边缘返回手势可能被吃 |
| 误判时用户点不动 | 有最长时长 + 解除按钮兜底 |
| 只能防点击型 | 摇一摇无效，见 R12 |

**验收**：测试台「全屏热区」样本连续 10 次不跳；跳过按钮仍能点掉；3 秒后自动撤除。

**定位**：默认关，实验开关；不适合直接进默认版本。

---

### 3.13 R12｜传感器前置：摇一摇在落地前被关掉（实验，P2）

**问题**：摇一摇全程没有点击，`TYPE_VIEW_CLICKED` 帮不上忙；而现有传感器方案只用于「提速」。

**改法**

1. 只在**冷启动监测窗口内**（≤10 秒）注册 `TYPE_ACCELEROMETER`，窗口结束立即注销 —— 后台零成本。
2. 识别「冲击—回弹」特征（单轴峰值 + 反向回弹，300~1200ms 窗口）。
3. `广告指纹确认 && 检测到摇动` → 立刻执行「跳过/关闭广告」动作（不是多按一次返回，也不增加任何一次回退）。
4. 抢赢 = 一次跳转都不发生；抢输 = 现有兜底照旧。

**风险**：误摇（走路、骑车）在无广告页上不会触发（有指纹门禁）；有指纹但用户自己想摇 → 关掉广告也无害。

**验收**：测试台摇一摇样本，落地率从 ~100% 降到 < 20%（🔶目标值待基线）。

### 3.14 R13｜目的地入口证据（先离线验证，P2）

**问题**：所有证据都在来源侧，没有一条看「结果」。

**改法**

1. 目的地首帧 `e.className` 与其 `getLaunchIntentForPackage(dest)` 的组件名比对：

```
不相等 → 大概率 deeplink 进入（广告）
相等   → 用户点图标 / 通知（用户意图）
```

2. 先**不写代码**：现有日志已有 `evt ... cls=`（[L678](../app/src/main/java/com/miaotiao/adskip/service/SkipAccessibilityService.kt#L678)），拿历史日志 + `adb shell cmd package resolve-activity --brief -a android.intent.action.MAIN -c android.intent.category.LAUNCHER <pkg>` 统计命中率。
3. 若「被拦的落地页大多是非 launcher Activity」→ 作为**佐证**加入；否则放弃。

**风险**：很多 App 的 deeplink 也走主 Activity（淘宝 `WelcomeActivity`），信号可能很弱 🔶。

### 3.15 R14｜Shizuku 精准模式（可选，P3）

**改法**：通过 Shizuku（shell 权限）读 `dumpsys activity activities` 或 `IActivityTaskManager`，拿 `launchedFromPackage` 与 `baseIntent`：

```
launchedFromPackage=com.xingin.xhs  intent=VIEW tbopen://...  → 广告跳转，拦
launchedFromPackage=com.miui.home   intent=MAIN/LAUNCHER     → 用户打开，放
```

这是唯一**非推断**的信号。代价：用户要装 Shizuku；`dumpsys` 解析脆弱（ROM 差异）；只在「可疑跳转」时调用一次（~100-300ms，事后无感）。

**定位**：高阶开关，不做默认；与「纯无障碍、不 root」的定位不冲突（Shizuku 不是 root）。

## 8. 不建议的方向（附理由）

| 方向 | 为什么不 |
|---|---|
| 继续加布尔信号 / 调时间窗 | 边际收益递减：窗口内本来就不区分「原因」 |
| 恢复坐标学习 | 已证明会稳定误点，v1.1.0 移除是对的 |
| 常驻截图 + OCR | 隐私 + 耗电，且回答的还是「像不像广告」 |
| VPN / DNS 拦截 | 摇一摇落地是本地 deeplink，不过网络 |
| root 屏蔽传感器 | 与「纯无障碍、不 root」定位冲突 |
| 电商 App 一律不拦 | 等于放弃功能，不是降低误拦 |

补充两个「系统能力」层面的缓解（写进引导页，不需要代码）：

- 关闭目标 App 的「支持的应用链接」（对 http(s) deeplink 有效，对自定义 scheme 无效）。
- Android 13+ 的「传感器关闭」快捷开关可根治摇一摇，但代价是全局丢传感器，只适合极端用户。

## 10. 一句话

> 最「优」的方向不是把「来源像不像广告」猜得更准，而是把判定换成
> **「这次跳转前有没有用户输入」×「当时屏幕上有没有广告」**，
> 并把「拿不准」从「自动回退」改成「一键撤销」。
> 前者消掉误拦的因，后者兜住误拦的果。

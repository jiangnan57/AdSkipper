# 防跳转的六条优化思路，和一次全机型适配性检查

> 秒跳（AdSkipper）v1.3.9 · 2026-11-23
> 对象：Android 无障碍工具里最难写的那半个功能——**把用户从广告落地页拉回来**

---

## 结论先行

1. **天花板在能力，不在代码。** 无障碍服务看得到窗口树，看不到 Intent、看不到传感器、看不到点击落在哪个 View 的哪个 SDK 上。所以「零延迟拦截」不存在，能做到的是「闪一下再回来」。既然如此，优化的目标就不是延迟，而是**误拦率**（用户能感知、会卸载）和**可见闪烁时长**（用户能容忍）。
2. **六条思路里最值钱的是「点击溯源」。** 现在的判定本质上是在猜「来源 App 像不像在放广告」；而「这一次跳转之前用户到底有没有点屏幕」是一个可以直接观测的事实。摇一摇广告全程没有点击，用户点商品卡一定有。
3. **适配性检查的结论有点反直觉：本机没有缺口，缺口全在别人的手机上。** 这台 Redmi（Android 17 / HyperOS 4.0.3）上权限、无障碍、白名单、名单覆盖、Lint 全部干净；真正会让新用户「装了没反应」的是三件与本机无关的事——Android 13+ 的受限设置、悬浮窗权限的真实作用、非小米 ROM 的桌面进程名。

## 一、先量一下天花板

| 想知道的事 | 无障碍能拿到吗 |
|---|---|
| 前台是哪个 App | ✅ 包名 |
| 界面上有什么控件、文案、坐标 | ✅ 节点树 |
| 这次跳转是谁发起的 Intent | ❌ |
| 手机被摇了吗 | ❌（传感器不在无障碍手里） |
| 用户刚才点的是广告还是商品卡 | ⚠️ 只有 `TYPE_VIEW_CLICKED` 这一条路，且 WebView 内部不一定派发 |
| 跳转发生在哪个窗口、是不是小窗 | ⚠️ 需要 `flagRetrieveInteractiveWindows`，本机实测打开后窗口列表会变成过期快照（见 `accessibility_service_config.xml` 注释），所以关掉了 |

这张表决定了所有优化的形状：**只能事后补救，只能靠旁证推断意图。**

现有判定的形状是「10 条 if 的链」，靠一组布尔量（`cold` / `settled` / `showingSplash` / `adProne`）推断「来源像不像广告」。这套东西能跑，但它有一个反复发作的病：**名单或信号只要有一个环节没接上，整条链就静默失效**。过去四个版本里，同一个病发作了四次：

| 版本 | 病症 | 后果 |
|---|---|---|
| v1.3.4 | `isBlocked` 命中就提前 return | 被拦名单里的 App 永远当不了「来源」，dt 全算错 |
| v1.3.4 | contentPage 统计放在规则命中之后 | 「已进正片」闸门永久失效 |
| v1.3.7 | 安装器写进 `STORES` | 用 MT 管理器装 APK 被弹回，装不了软件 |
| v1.3.8 | 负一屏在 `NEVER_SCAN` 里，判定链读不到 | 从负一屏点拼多多，一分钟连弹五次 |

所以下面的思路，一半是在加新信号，一半是在**拆掉「靠 if 顺序兜底」这个结构**。

## 二、六条思路

排序依据是「收益 ÷ 风险」，不是「技术含量」。

### 思路 1：点击溯源——把「意图」变成可观测事实（首推）

**现状**：判定靠「来源像不像在放广告」。用户自己在详情页点了商品卡，和摇一摇落地，在时间线上完全重叠（都是 5 秒内、都是冷启动、来源都没进正片），只能靠名单硬分。

**事实**：这两件事有一个决定性区别——**有没有一次点击**。

**做法**：
- `accessibilityEventTypes` 加 `typeViewClicked`（`flagReportViewIds` 已经有，不用动别的）
- 收到点击就记 `(pkg, 节点文案, 时间)`，只留最近一次
- 判定时加一条：`now - lastTapAt < 1500ms && tapPkg == origin` → `KEEP("用户刚点了「加入购物车」")`

**收益**：
- 直接消掉「用户自己点商品卡被弹回」这一整类误拦，比调时间窗、调名单都准
- 日志从「来源不像广告（cold=true settled=false）」变成「你 0.4 秒前点了『立即购买』」——用户反馈的质量完全不同

**代价**：WebView 内部的点击有时不派发事件 → 该拦的漏拦。方向是对的（漏拦只是多看两秒广告，误拦是用户打不开 App）。

**风险控制**：这条只做「否决」（有点击就不拦），不做「确认」（没点击也不等于就是广告，仍走原判定）。所以它**只会减少拦截，不会增加**。

### 思路 2：摇一摇的传感器旁证——只提速，不参与决断

**现状**：检测到落地页 → 等 400ms 才按返回。为什么等？因为落地页还在冷启动时返回键会被它的欢迎页吃掉（淘宝实测连按两次没反应）。这 400ms 就是用户看到的「闪一下」。

**做法**：前台服务注册加速度计（无需任何权限），检测「冲击—回弹」特征，记一个 `shakeAt`。若落地时 `now - shakeAt < 2500ms`，把返回延迟从 400ms 压到 ~80ms。

**关键设计**：传感器**只用于决定「多快返回」，不用于决定「返不返回」**。这样即使把走路、骑车识别成摇晃，也不会多拦一次——风险被结构性地消掉了。

这也是它排在思路 1 后面的原因：收益是「闪烁从 400ms 变 80ms」，属于体验优化，不是正确性问题。

### 思路 3：判定结构从「布尔链」改成「硬否决 + 证据分」

**问题**：四次事故的共性不是「某个包名写错」，是「**一条 if 的顺序决定一切，而顺序会被人改**」。

**做法**：
- 把所有「一定不拦」的条件固化成**硬否决集合**（同包切换 / 目的地是用户已打开的 App / 来源是外壳 / 停留过短 / 刚拦过）
- 把「像不像广告」改成**证据加权**：`cold`、`showingSplash`、`dt` 落在哪个区间、有没有点击、有没有摇晃、目的地类型、来源是否广告高发——每条给一个权重，超过阈值才拦
- 输出 `score + 命中的证据列表`，整条进日志

**收益**：新信号（点击、摇晃、窗口层级）可以平滑加进去，不用重排 if；判定过程可解释、可回归。

**代价**：加权模型天然比布尔链更难推理，容易变成黑盒。折中是「否决仍然硬编码，权重只用于正向判定」，并且**要求每条证据都必须出现在日志里**——看不到证据的权重不许上线。

### 思路 4：名单从「硬编码」改成「问系统 + 远程下发」

这条本次已经落地一半。

**问题**：桌面进程的名字毫无规律。`com.miui.home` 里连 `launcher` 这个词都没有；AOSP 的兜底桌面 `FallbackHome` 干脆住在 `com.android.settings` 里。靠静态名单 + 包名特征猜，换个 ROM 就得等用户反馈再发一版。

**做法**：能处理 `CATEGORY_HOME` / `ACTION_ASSIST` / `ACTION_ALL_APPS` 的包，直接当系统外壳——「谁是桌面」这件事系统本来就有权威答案。

**必须排除 `SYSTEM_UI`**：`com.android.settings` 会作为兜底桌面被枚举出来，但设置页的语义是「透明层」（用户跳去授权再返回，来源上下文必须保留）。混进「桌面」名单会导致 reset，返回时来源变 null，防跳转在那几分钟里等于关掉。同一个包挂两份名单、靠判断顺序决定结果——这正是前面那四次事故的成因，所以这次在**生成阶段**就让两份名单互斥。

**还剩一半**：`AD_LANDING` / `CONTENT_APPS` / `AD_PRONE` 仍靠人肉维护。这些完全可以走已有的远程规则通道下发，出新广告主不用发版。

### 思路 5：拦截时序 + 可撤销

- **0ms 先探一次前台**：现在无条件等 400ms。其实可以先读一次 `rootInActiveWindow.packageName`（约 30ms），如果前台已经是落地页就立刻按返回，400ms 那一路保留作兜底。省掉一半以上的闪烁。
- **误拦要能撤销**：拦完发一条通知「拦住了一次跳转 · 撤销」。点撤销 = 拉起原落地页 + 5 分钟熔断 + 记一笔学习。现在用户不同意判定的唯一出路是「再点一次」，靠的是 `RepeatGuard` 的 3 次熔断——这个反馈太隐晦了。

### 思路 6：一键诊断包

社区分发最痛的不是 bug，是**隔着屏幕判断不了是权限问题还是名单问题**。导出一份 `ROM / API / 权限 / appops / 最近 200 条 / 名单命中统计 / 服务存活时长 / 已安装包分类结果`，一个人发一份就能定位。现在只能让用户截图「最近记录」。

### 3.3 三个高危缺口（都在「别人手机」上）

**① Android 13+ 的受限设置**

从浏览器、QQ、网盘侧载的 APK，系统会把它标记为「受限设置」：**无障碍开关是灰的，点不动，也不告诉你为什么**。用户只会说「装了没用」。

本机查不出来——这里是 `adb install`，`installerPackageName=null`，不触发。但只要用户正常下载安装就一定会遇到。社区分发必须给一句明确的话：「设置 → 应用 → 秒跳 → 右上角三点 → 允许受限设置」。

**② 悬浮窗权限不是「让识别更稳」，是「能把 App 拉回来」的前提**

AOSP 对后台启动 Activity 的豁免里，`SYSTEM_ALERT_WINDOW` 和「有可见窗口」是两条主要通道，而这个 App 的 1×1 透明窗（ghost window）本身就要靠这个权限才加得上。也就是说：**没有悬浮窗权限 → 三级兜底的第 2 级（拉起原 App）会静默失败，只剩第 3 级回桌面。**

现在的首页文案写的是「悬浮窗权限未开 → 后台识别会失效」，把后果说轻了。这是推断（本机两条通道都满足，没法反证），但方向明确：应该按「必需权限」对待。

**③ 桌面/负一屏名单是静态的**

见思路 4。`com.miui.home` 不含 `launcher` 一词，`FallbackHome` 住在设置包里，靠猜是猜不全的。

### 3.4 本版改了什么

只改了两处，都是检查直接查出来的：

1. **`AppLists.loadRuntimeShell()`**：服务连接时枚举 `HOME` / `ASSIST` / `ALL_APPS`，把结果并入系统外壳；`mergeRuntimeShell()` 排除系统 UI 包。查询抛异常时退回纯静态名单，不会整体失效。
2. **`STORES` 补两家**：`com.sec.android.app.samsungapps`（三星）、`com.hihonor.appmarket`（荣耀）。漏一个不是「少拦一次」，是那个 ROM 的用户完全用不上——商店是唯一「不限来源」的拦截目标。

**验证**：
- JVM 单测 **74/74**（原 69，新增 5 条：运行时名单命中、排除系统 UI、清空后回退静态、商店齐全）
- 真机：`runtime shell=2 [com.miui.home, com.miui.voiceassist]`
- 真机：桌面点拼多多 → `guard pkg=com.xunmeng.pinduoduo ... origin=null dt=-1ms -> KEEP 没有来源 App`
- 真机：B 站冷启动监测 27 轮 / 425ms，链路正常

### 3.5 没有设备就不下结论的项

这些不写「应该没问题」，写「没测」：

- 三星 / 荣耀的商店包名是按公开名称补的，**未实测**
- 折叠屏、分屏下 `displayMetrics` 的取值（历史遗留：小窗里它恒为整屏尺寸，`strictAdPage` 这类比例判据会失真）
- 多用户 / 工作资料下的桌面与无障碍状态
- 各家 ROM 的「无障碍自动关闭」策略（ColorOS、EMUI 都有超时关闭，目前的兜底是 60 秒失联自愈）
- targetSdk 升到 35/36 后的 edge-to-edge 布局

## 四、怎么复现这份检查

```bash
# 1) 单元测试
./gradlew :app:testDebugUnitTest

# 2) 静态检查
./gradlew :app:lintDebug
# 报告：app/build/reports/lint-results-debug.html

# 3) 真机枚举系统外壳（和 App 里跑的是同一套 Intent）
adb shell cmd package query-activities --brief -a android.intent.action.MAIN \
    -c android.intent.category.HOME
adb shell cmd package query-activities --brief -a android.intent.action.ASSIST

# 4) 看 App 自己算出来的名单
adb logcat -s AdSkip | grep "runtime shell"

# 5) 功能复核：从桌面点开一个电商 App，应该看到
#    ... guard pkg=com.xunmeng.pinduoduo ... origin=null -> KEEP 没有来源 App
```

## 附：这个项目的取舍原则

写在这里，因为它是所有判定的隐含前提：

> **漏拦的代价是广告多看两秒，误拦的代价是用户打不开 App。**
> 两者不对等，所以所有拿不准的地方一律往「不拦」倒。

这条原则解释了很多看起来「保守」的选择：多窗口一律不判定（小窗里看小说被弹回，书页和进度一起没了）、停留不足 500ms 一律放过、1 分钟内连拦 3 次就熔断 5 分钟、内容型 App 的门槛比电商高一档。它们不是漏判，是刻意的。
